# Session 06 — Views, and the First Screen Anyone Has Ever Seen

The repertoire filter the product has needed since the import landed. Also the session in which
the app **ran on something for the first time** — and crashed on launch, for a reason no test in
the suite could have caught.

## Where we are

- **Views are landed and working on an emulator against the real 479-song database.** A View is a
  saved pairing of *which songs are eligible* (performer × instrument capability) with *which
  instrument the session is about* (log target and staleness scope). Contract:
  [views.md](../decisions/views.md), V1–V31.
- **The motivating case is proven end to end.** Filter `(Will, vocal, lead only)`, practising
  guitar → **231 songs, 138 never practised on guitar**, confirmed three independent ways: the
  shared-core query, a direct `sqlite3` count on the device, and a full scroll-and-scrape of the
  rendered list.
- **176 tests, 0 failures**, from a clean build with `--rerun-tasks --no-build-cache`.
- **Nothing is committed.** The whole feature sits in the working tree.
- **Nothing has run on physical hardware.** An emulator is not a phone.

## The bug that started it

The user reported that selecting the "vocals" pill did not filter out songs they will never sing.
It was a UI gap, not an import defect, and the diagnosis is worth keeping because the instinct
"probably a DB error too" was wrong in an instructive way.

`song.sq :: selectByStaleness` used `instrumentId` **only in the `LEFT JOIN … ON` clause**. The
chip scoped *which history counts toward staleness* and nothing else; every live song was always
in the list. There was no repertoire filter anywhere in the app.

The import was sound. Of **368 vocal practice events, 363** fall on songs where Will is marked
lead — the capability data predicts what he actually sings with ~99% accuracy, which is what made
`song_performer` a defensible filter key rather than a guess.

The 479 songs break down as: **231** Will lead, **3** Will non-lead, **98** someone else only,
**147** no performer data. The 98 are the clutter — *Ain't No Sunshine* (Newton), *All About That
Bass* (Coralie/Ryan/Sophie-Mae) — and he practises them 55 times on guitar, bass and keys and
twice on voice. That pattern is what settled the design: the fix had to be **per role**, not
global.

## Decisions this session

Full contract in [views.md](../decisions/views.md). The ones that matter:

- **V1 — `song_performer` gained `instrument_id`**, turning "who sings this" into "who does what
  on this". `song_instrument` was the obvious-looking alternative and is a trap: it holds 132 rows
  (bass 93, guitar 31, keys 8, **vocal 0**) of per-instrument *facts*, so filtering the pill on it
  would show an **empty list on the vocals chip**.
- **V3 — the first three-key junction.** `song_id/performer_id/instrument_id`, amending data-model
  decision 4. Every existing `song_performer` id changed; safe only because the table is rebuilt
  wholesale and no device has synced.
- **V13 — one instrument field, not two.** The View's practice instrument is both what it logs to
  and what staleness is measured on. The filter instrument is separate, which is the whole point.
- **V13a — a chip tap forks to an unsaved View and never edits the saved row.** `saved_view` is a
  synced row; a mid-practice thumb-press must not rewrite configuration on every device.
- **V19 — the home View is a local preference, never a column.** An `is_home` boolean across rows
  has no total order under last-write-wins: two devices each promote a different View, both stay
  true, and no sync repairs it.
- **V12a — the sort has no performer dimension and must not grow one.** `practice_event` has no
  performer column because every event is the owner's.

## Reversals — three, all mine, all caught by something outside my own reasoning

Recorded in full, because the pattern is the lesson: **every one was a plausible inference I wrote
into the spec as a fact, and every one was refuted by real data or an independent reader.**

1. **V27 blamed the wrong column.** I attributed Will's three non-lead rows to `Will plays`. That
   column is **entirely empty**; the rows come from `Demo 2022`, which V26 deliberately keeps at
   non-lead. Caught by the implementing agent running the migration instead of trusting the spec.
   Now V27a.
2. **The V14 worked example was fiction.** It claimed *9 to 5* had never been practised on guitar.
   It was, on 2026-05-13. Now uses *A Whole New World*, with every value lifted from the migrated
   database.
3. **V22 was actively harmful and I reversed it.** It cleared the session's optimistic taps on a
   View switch. The style reviewer showed that breaks the ordinary guitar → bass → guitar flick,
   which today returns you to your logged list. It was also unnecessary — `tapsHere` already scopes
   by instrument and `logged` drops songs absent from the current View. V22 now clears only the
   undo offer.

Also corrected: **V17 claimed a third sort direction was "a one-line change". It is three** — the
enum constant, the SQL `CHECK`, and the parse. V17a now requires a test pinning the enum against
the `CHECK`.

## The crash, and why nothing caught it

The app **crashed on launch** the first time it was ever run.

```
java.lang.NullPointerException: ... MutableStateFlow.setValue(...) on a null object reference
  at dev.repertaurus.android.SessionViewModel$loadPerformers$1.invokeSuspend(SessionViewModel.kt:348)
```

A Kotlin **property initialisation-order hazard**. `init { reload() }` sat at line 68; `reload()`
calls `loadPerformers()`, which writes `_performers` — declared at line **341**. `viewModelScope.launch`
uses `Dispatchers.Main.immediate`, so the coroutine starts eagerly on the calling thread and the
small performer query can resume *before the constructor has finished initialising its own
properties*.

**`_homeViewId` at line 85 carried the identical defect** and survived only because `reload()`'s IO
path runs `SampleData.installIfEmpty` over 479 songs — slow enough that construction always won the
race. Luck, not design. It would have fired on a small or empty database, i.e. on a fresh install,
after shipping.

The fix moved `init { reload() }` to the **bottom of the class body**, which makes the hazard
structurally impossible rather than defending two known properties. The class is organised into
feature sections that each declare their own `MutableStateFlow` beside the methods using it — a
shape that actively invites the next such property. Verified by eight `pm clear` + cold-launch
cycles against a freshly seeded sample database, the exact fast path the old ordering could not
have survived.

**Why 176 tests and three code reviews all missed it: `androidApp` has no test source set.** Nothing
anywhere constructs `SessionViewModel`. A single test that does nothing but construct it against an
empty database and read `performers.value` would have caught this. **This is the most valuable
thing to fix next.**

## Process lessons

1. **Run it. The emulator paid for itself in one launch.** Three reviewers, 176 passing tests and a
   clean build all said green; the app did not start. `adb` + `screencap` + `uiautomator dump` is
   cheap and is now the standard for "done" on anything with a screen.
2. **Reviewers who re-measure beat reviewers who read.** The safety reviewer independently
   recomputed all 595 ids in Python and ran all eight filter combinations against the real
   database rather than trusting the author's numbers. The implementing agent found the V27 defect
   the same way. Every correction this session came from someone re-measuring.
3. **`BUILD SUCCESSFUL` is still not evidence** — session 05's lesson, and it held again. Every
   test run this session used `--rerun-tasks --no-build-cache` and the task was confirmed
   `executed`.
4. **The NUL byte in `DatabaseHolder.kt` bit again, live.** Grepping it for `getDatabasePath`
   returned "no matches found" — not absence, but ripgrep silently classifying the file binary.
   **Escalate this from a note to a fix**; it produces confident false negatives.
5. **A verification harness can validate a copy of the thing instead of the thing.**
   `build.py :: verify()` embedded a hand-transcribed copy of `selectByStaleness` and reported its
   numbers back as proof. It now extracts the query from `song.sq` at run time.
6. **Write the loud failure where the value is actually missing.** `build.py`'s "carries no
   instrument" guard could never fire, because `extract.py` defaulted the instrument two steps
   earlier. Harmless while all 595 rows are vocal; lethal the moment hand-entered guitar data
   arrives. Now V30.

## Open

- **`androidApp` has no test source set.** See above. Highest-value next item.
- **A `Will/Coralie` performer row exists with zero capability rows.** A duet marker (`W/C`) that
  should resolve to two people has also seeded a combined performer. Inert in the data — correctly
  excluded from `song_performer` as staging-only per decision 58a — but it **appears in the View
  editor's performer picker**, and choosing it yields an empty View. `Carla` also has zero rows and
  that one is deliberate ([R13] seeds a performer per singer column even when empty).
- **The `507` vs `595` discrepancy.** The repo recorded 507 `song_performer` rows as a *measured*
  figure since session 04; the real count is 595, and nothing in this session's work adds 88 rows.
  The old number was stale or wrong. **Not yet established which**, and it should be, because a
  corrected number sitting on top of an unexplained one is how the next wrong inference survives.
- **No capability data for guitar, bass or keys.** V1 makes it expressible; the workbook does not
  contain it. A guitar-filtered View is empty until it is entered by hand, and **no data-entry UI
  is specced**.
- **Deferred review findings, deliberately not actioned**: Compose stability configuration for the
  shared-core types; `collectAsState` calls hoisted too high in `SessionScreen`; per-row
  memoisation of the switcher's summary strings; `ViewFilter`'s two adjacent nullable `String`
  parameters being silently swappable; `SessionView.UNSAVED_ID`'s empty-string sentinel.
- **One benign out-of-order write remains**: two rapid chip taps can land their
  `SharedPreferences` instrument writes in either order. Local, never synced, both values valid.
- **The View editor shows no row count**, which made proving "231" a full scroll-and-scrape. A count
  in the top bar's second line would pay for itself.
- Carried forward untouched: `practice_context` unreachable from the UI, no song editing, the
  phase 2 sync spec unwritten, and the `jvm()` target still the cheapest structural win.

## The second crash — and the one that mattered

The first delivery **crashed on the user's phone**, and then survived a full
uninstall–reinstall–reimport. That second failure is the important one, because it proved the first
diagnosis was incomplete.

Measured, not guessed — the three database files in the delivery folder:

| file | `user_version` | passes the import check | has `saved_view` |
|---|---|---|---|
| `songbook-2026-08-16.db` | 1 | yes | **no** |
| `songbook-2026-08-16b.db` | 1 | yes | **no** |
| `repertaurus-2026-08-16-views.db` | 1 | yes | yes |

**All three are indistinguishable to the app.** Importing either obsolete file succeeds, and the app
then dies on next launch with `no such table: saved_view` — thrown on the start-up path, before any
screen is drawn, and therefore **before the import UI that could fix it is reachable**. A database
the app cannot read made the app unrecoverable from the device.

Three stacked failures, all mine:

1. **The schema version never moved.** `saved_view` and `instrument_id` were added with no `.sqm`,
   so `Schema.version` stayed at 1 and every database claimed to be version 1.
2. **The import validator checked a phase-1 snapshot** — a hardcoded five-table count — instead of
   what the build actually needs, so it accepted a file guaranteed to crash the app.
3. **The boot path had no failure mode short of a crash.**

A fourth, on me as the deliverer: I left **three `.db` files** in the folder, two named for the old
brand, and said "import the .db" without naming which.

The contract is [schema-compatibility.md](../decisions/schema-compatibility.md), S1–S13. **S8 is the
rule worth carrying: the app must never hard-crash on any database state, in alpha as much as in
release.** The user's wording stands verbatim in the spec.

Landed: `Schema.version` = 2 with a real `1.sqm`; one `SchemaCompatibility` used by **both** the
import path and the boot gate (they disagreed, which is why the bug existed); a `RecoveryScreen`
that replaces the whole tree so recovery never routes through the screen that cannot load; and an
`androidApp` test source set — 24 tests in the layer that had none.

**The reviewers caught a data-destroying defect in the fix itself.** `SQLiteDatabase.openDatabase`
with no error handler installs `DefaultDatabaseErrorHandler`, **which deletes a corrupt database**.
The gate written to protect the user's data would have destroyed their only copy. It was measured
with a probe — the file *was* deleted — then fixed on both the raw open and the driver, with a test
asserting the file survives.

## The same bug shape, three more times

`tools/import/build.py` hardcoded `SCHEMA_VERSION = 1` under a comment claiming it was read from the
generated schema. It was a literal, and it was wrong: the shipped database carried v2 content
stamped version 1. The fix **derives** the version from the checked-in `.sqm` files, cross-checks it
against the generated schema, and aborts on disagreement, on a missing cross-check, or on
non-contiguous migrations. All three guards were proven by constructing inputs that trip them.
Replacing the literal `1` with a literal `2` was explicitly rejected as re-arming the trap.

The same agent then found `build.py`'s insert order was a **hardcoded 17-table roster** — a table
added to the schema would be silently skipped and still produce a complete-looking database. Now
derived from the `.sq` files with deliberate exclusions named.

**Still outstanding, and now the highest-value item:** `JUNCTION_KEYS` exists as two hand-maintained
copies, in `extract.py` and `Uuid.kt`. They agree today and each comments the other, but **nothing
enforces it** — and that map exists precisely to prevent silent wrong-id forks. This is the same
class of defect as the other three, in the one place the project has already been burned twice.
