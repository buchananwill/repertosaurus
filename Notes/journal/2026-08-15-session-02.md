# Session 02 — Normalisation Pass and Adversarial Schema Review

Still no code. The schema contract was revised twice: once by a normalisation pass, then again
after an adversarial review found defects that would have shipped.

## Where we are

[data-model.md](../decisions/data-model.md) is at 60 decisions and is believed sound.
[import-songs-2026.md](../migration/import-songs-2026.md) has been brought back into agreement
with it. Nothing has been dispatched to an implementing agent. Next action is phase 0.

## Normalisation pass

The user directed that `discipline` become a table and asked for another pass. Seven further
changes resulted:

1. **`instrument` absorbs discipline**, and unifies with gig-sheet instruments. Voice is an
   instrument here. Two vocabularies — one for practice, one for line-ups — would drift apart.
2. **`performer` table, plus `song_performer`.** This closed a real gap: the first spec fixed
   "a column per singer" at set list level and then dropped the song-level fact entirely, so
   the master sheet's `Lead vocal` and `Coralie Vox` columns had nowhere to land. Two distinct
   facts now: who *can* sing it (`song_performer`) and who *did* at this gig
   (`setlist_item.lead_performer_id`).
3. **`vocal_range` moved onto `song_performer`.** Range is only meaningful for a particular
   voice. With one performer it reproduces the workbook exactly, so it costs nothing now.
4. **`song_instrument`** — per-song, per-instrument facts, absorbing `bass difficulty`,
   `Guitar comments`, `BV Comments`, `C GTR`, `Wavestate Patches`, all of which the first spec
   silently dropped.
5. **`tonal_centre` became an integer pitch class 0–11**, not a note name, so transposition is
   modular arithmetic and enharmonic spelling is derived from the key signature.
6. **`tag`, `venue`, `groove` as lookups**; `setlist_set(set_no, target_minutes)` replacing the
   `2x60` string so no UI ever parses text to total a set.
7. Restored song structural fields the first spec lost: `loop_length`, `chord_count`,
   `chord_pattern`, `groove`, `mashup_note`.

Naming collision resolved: `practice_event.feel` keeps the user's word for the 1–3 rating; the
workbook's musical `Feel` column became `song.groove`.

## The review — read this before simplifying anything

A review agent was dispatched against the revised spec with a mandate to find defects, not to
approve. It found eighteen; roughly fifteen were accepted. The four that mattered most were all
defects that would have reached production code, and three of them were self-inflicted —
decisions that contradicted other decisions in the same document.

**1. Type-ahead-creates plus last-write-wins produced unmergeable duplicates.** Every lookup is
created by a type-ahead on either device with a random UUID. Two devices offline both type
"wedding" and produce two rows with different ids and the same name. LWW compares rows by id,
so it never compares them; the union rule does not apply. Nothing converges them, and the spec
forbade the admin screen that would let a human fix it. This reproduced `Party`/`party` — the
exact failure the normalisation test exists to prevent — one indirection deeper, where it is
invisible in the UI.

*Fix:* derived ids. `UUIDv5(namespace, normalised_name)` for lookups and
`UUIDv5(fk_a, fk_b)` for junctions, so both devices independently generate the same id and LWW
resolves the rest. The general rule is now decision 3: **derive the id where a duplicate is an
error, randomise it where a duplicate is meaningful.** `practice_event` must stay random,
because two taps on the same song in a day are two real sessions.

**2. Undo was unimplementable on the highest-frequency path.** The spec said a mistaken practice
event is "corrected by writing a tombstone", but the column list had no `deleted_at`, the
tombstone rule applied only to mutable tables, and the event table merges by *union* — which
has no way to suppress a row. A mis-tap that had already synced would return on the next merge.

*Fix:* `practice_event_void`, a second append-only table that also merges by union, left-anti-
joined on read. Preserves the two-rule invariant rather than adding a third.

**3. The ordering column violated the spec's own sync invariant.** One decision forbade
monotonic counters; another made `setlist_item.position` an integer index. Two devices
reordering offline — one inserting and shifting ten rows up, one deleting and compacting three
down — merge per-row into duplicated positions and holes.

*Fix:* fractional ordering keys (LexoRank-style) so a move touches exactly one row, which is
what LWW can actually merge.

**4. The migration destroyed major/minor for the entire repertoire.** Mode is implied by the
`(key_signature, tonal_centre)` pair — but only when the signature is non-null, and the
migration set it NULL for all ~460 songs. `E` and `Em` both import as `tonal_centre = 4,
key_signature = NULL` and become the same row. The premise was also wrong: a named key *with
quality* is isomorphic to a key signature, so the signature is derivable by arithmetic for all
2,121 plain-name cells without any musical analysis.

*Fix:* derive `key_signature` from the named quality on import. Nullability is retained for the
15 genuine unknowns and for honestly modal songs.

Also accepted: a total order `(updated_at, device_id, id)` on LWW, because same-millisecond
edits otherwise diverge permanently; fixed-width timestamps, because `...:00Z` sorts after
`...:00.500Z` when `Z` > `.`; a circle-of-fifths reduction rule preferring the smaller
`|key_signature|`, because C major transposed up a semitone otherwise renders as C♯ major with
seven sharps; `backing vocal` as its own instrument, so a song can carry both a lead and a
backing note without two rows for the same pair; `setlist_item.setlist_set_id` as a real
foreign key instead of an integer compared by value; and four missing migration rules —
performers, venues, `setlist_set`, and the duration and tempo data the spec had diagnosed and
then thrown away.

### Where the review was not followed

- **`chord_pattern` stays free text.** The reviewer applied the normalisation test correctly,
  but the field is rarely populated over a vocabulary that is not closed. The lookup table
  costs more than the drift risk. Recorded as decision 30 so it reads as a judgement, not an
  oversight.
- **`artist_alias` is kept**, though narrowed. The reviewer was right that all seven known
  spelling collisions collapse under the normalisation function alone. It survives for aliases
  normalisation *cannot* reach — `OCS` for `Ocean Colour Scene` — and decision 22 now says so
  explicitly and forbids populating it with cases normalisation already handles.
- **`tonal_centre` keeps the "home bass note" definition.** The reviewer found a genuine
  ambiguity against the "first or last chord" wording and proposed deleting the bass-note
  phrasing. That phrasing is the user's own definition, so the fix instead made the chord rule
  an explicit *tie-break* subordinate to it, and pinned it to the chord's root rather than its
  sounding bass.

## Decisions carried from the user this session

- `discipline` is a table (now `instrument`).
- Double-logging a piece in one day is **not** a data error. Working the same piece several
  times across a day is normal and each pass is a substantive session. No uniqueness
  constraint, and undo must be real rather than something a constraint swallows.

## Open questions

Unchanged from session 01, minus the key-signature backfill, which is now largely solved by
derivation at import. Still open: the `Order` column's per-tab ambiguity; song duration beyond
what rule 28 recovers; web UI scope.

## Process note

The review was worth its cost and should be repeated before any spec is handed to implementers.
Three of the four serious findings were **internal contradictions** — decisions in the same
document that could not both hold. Those are exactly what a fresh adversarial reader catches
and an author does not.
