# Session 01 — Diagnosis, Data Model, Stack, Delivery Order

First session. No code written. This entry establishes the thread: what the project is, what
was decided, what was reversed along the way, and what remains open.

## Where we are

The repository exists with documentation only. Nothing has been dispatched to an implementing
agent. The next action is phase 0 (the import script) and phase 1 (the Android app), described
in [stack-and-delivery.md](../platform/stack-and-delivery.md).

The design proposal that seeded this repo was developed as a published artifact at
`https://claude.ai/code/artifact/3192a9e9-d68f-4a23-a954-5a5b0661776f`. **It is no longer the
source of truth** — the documents in `Notes/` are. The artifact remains useful as a narrative
summary for a human reader, but do not implement from it.

## The problem, evidenced

The source workbook is `Songs 2026` (Google Sheets, id `1WWeDvYJ5FMUFcZg5MYX6Fe7oLyYrrfnk5jqNTnz_flA`,
owned by `stampy.the.elephant@gmail.com`). 57 tabs, 4,049 exported rows. Findings that drove
the design, all computed from the live file rather than estimated:

- **Practice logging decayed to nothing.** De-duplicated `(song, discipline, date)` events by
  year: 2022: 605, 2023: 149, 2024: 73, 2025: 13, 2026: 18. Not a drop in practising — a drop
  in recording it.
- **Logging destroys history.** Practice columns hold a single date. Of 589 song/discipline
  pairs carrying a date, 385 hold exactly one; every earlier session was typed over. The 204
  that hold more survived only because a stale copy froze in a set-list tab.
- **Counter columns were tried and abandoned.** The 2022 workbook had `Vocal Practise Number`,
  `Guitar Practise Number`, `Keys Practice number`. None ever received a value. They are gone
  from the 2026 master.
- **Copying, not authoring.** 460 distinct songs occupy 2,886 rows — 6.3 restatements each.
  *Valerie* appears in 40 of 57 tabs.
- **The `Key` column holds 58 distinct values doing five jobs**: 2,121 key names; 20
  transpositions written key-first (`D (-2)`, `Ab (-7)`); 3 written offset-first (`-7 (B)`,
  `+2 (G)`); 2 "deliberately original" markers (`Em (Orig)`, `Orig.`); 15 unknowns (`???`,
  `E?`); 44 cells that were never keys (`0` ×25, `2010` ×17, `TRACK`, `28/05/24`).
- **Artists drift.** 288 distinct artist strings representing 278 artists. `The Kaiser Chiefs`
  ×15 vs `Kaiser Chiefs` ×1; `Fratellis` ×10 vs `The Fratellis` ×2; `&` vs `and`; case.
- **Set structure is encoded in a decimal.** Running order stored as `0.2`, `1.09`, `2.03` —
  set number before the point, position after.
- **Two tabs share a client name** (`SO42 7QB - Mr & Mrs Anthony Horne`), 56 rows each,
  differing in five cells. Which was played is not recoverable.

## Decisions made this session

Recorded in full in [data-model.md](../decisions/data-model.md) and
[stack-and-delivery.md](../platform/stack-and-delivery.md). Summarised here with reasoning.

1. **Three jobs, separated.** Append-only practice log; canonical song facts; set lists as
   ordered references. The spreadsheet forced all three into one rectangle.
2. **`practice_event` is immutable and UUID-keyed.** Merging two devices is a set union, so
   sync has no conflict case for the high-frequency data.
3. **`artist` is a first-class table**, songs carry an FK. Adding one must stay a type-ahead
   that creates on enter — no admin screen, or it becomes the reason songs stop getting added.
4. **`context` is also a table, not an enum.** Same argument. The user must be able to add
   "wedding", "dep gig", "lesson" without a schema change.
5. **Key is three typed fields plus a reference recording**, not free text: `key_signature`
   (−7..+7), `tonal_centre`, `tonality_note` (hidden by default). Stated against a named
   recording so another musician can verify it.
6. **Transposition belongs to the performance, not the song.** `setlist_item.transpose`, a
   signed semitone count. Multi-select transpose-all on a set list is a day-one affordance for
   downtuned guitars.
7. **`feel` (1–3) is in the event schema**, surfaced as long-press. Decided by the user after
   initially being specced out.

## Reversals — read these before proposing alternatives

Four decisions were made and then overturned. Do not resurrect them without new information.

- **Postgres → SQLite.** Postgres was approved early, then carried through PGlite (WASM
  Postgres in a browser). Once the app became native rather than a PWA, WASM Postgres had no
  purpose. Local store is SQLite via SQLDelight. A Postgres *server* remains available as a
  sync adapter if one is ever wanted; the schema is unchanged either way.
- **PWA → native.** The original recommendation was a static PWA. The user rejected it
  explicitly: it must not "feel like a browser sandbox facade". This also ruled out Tauri, for
  the same reason — it is a webview, and the Session screen is a long scrolling list with swipe
  actions, which is the UI that most exposes one.
- **Flutter → Kotlin Multiplatform.** Flutter was recommended first, on a "feels native"
  argument that does not survive scrutiny: on Android, Compose *is* the first-party toolkit,
  not an imitation of it. The user's Java and React/TypeScript background makes Kotlin readable
  from day one. KMP also allows sharing only the logic, so a disappointing Compose-on-iOS can
  be replaced with SwiftUI over the same core. Cost accepted: Compose Desktop ships a JVM
  (~50–80 MB, ~1s cold start) against Flutter's AOT binary.
- **Google Drive → Dropbox.** Decisive and narrow: Dropbox issues refresh tokens to public
  PKCE clients with no server. Google will not — its browser flow returns a one-hour access
  token and no refresh token, because refresh requires a client secret that cannot ship in a
  client. An app whose premise is a three-second log cannot bounce the user to a consent
  screen. If Drive is ever wanted, it needs a ~30-line token-exchange proxy.

**React Native** was also considered and rejected: healthy in 2026, but no credible unified
desktop story, which would mean two UI codebases with the desktop one back in a webview.

## Open questions

- **Key signature backfill.** No key signature exists anywhere in the workbook, so ~460 songs
  need one that does not currently exist. Agreed to import as `NULL` and backfill later so it
  cannot block phase 1. The backfill UI (a "songs missing a key signature" queue on desktop) is
  not yet designed.
- **`Order` column semantics.** Several tabs use `Order` for the set.position decimal; others
  appear to use it for duration in seconds (values like `216`, `230`, `300`). The migration
  must disambiguate per tab, and this has not been fully resolved — see
  [import-songs-2026.md](../migration/import-songs-2026.md).
- **Song duration** is not reliably recorded anywhere, but the set list screen needs it to
  total against a booked set length. Source to be decided; likely manual or from a music API.
- **Web UI scope.** Agreed the web build is deliberately smaller than native (log, browse, view
  and print a set list — not set list building or bulk transpose). Not yet specced.

## Explicitly deferred

- **Schema migrations.** The user has ruled that losing a week of QA logging is an acceptable
  price for speed, and that migrations are not to be sweated "until there is a user who isn't
  me". Do not build migration infrastructure in phase 1.
- **Native iOS.** Deferred behind the web build, which reaches iOS users without a Mac, a $99/yr
  Apple account, or App Store review.

## Environment

- Development root is `D:\Coding\`. This repo is `D:\Coding\songbook`.
- Test device: **Samsung Galaxy S20, Android 13**. That is the phone the Session screen must
  feel right on.
- The user's split is roughly **70% phone / 30% desktop**. Phone is where logging happens;
  desktop is where songs get edited and sets get built. That split maps onto the merge rules —
  the phone only appends immutable events, the desktop does most of the mutation — so genuine
  write conflicts are close to impossible in practice.
