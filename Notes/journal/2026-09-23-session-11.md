## Decisions

- **D19. The habit arc is run from a roadmap**:
  [habit-arc-roadmap.md](../roadmap/habit-arc-roadmap.md), in a new `Notes/roadmap/` domain
  (`type: workflow`, `area: product`), added to the root index. **It is owned by the lead and
  amended in place.** The vision outranks it. It is not Piste Perfect's roadmap schema (session 10,
  D9 still stands). It is a plain workflow document inside this project's existing schema.

- **D20. Schema 3 is the critical-path keystone, and it is one migration.** This confirms session
  10 §4's "bundle every data change" proposal. The four data changes are:
  - ratings;
  - feel 0–3 plus `duration_seconds` (one `practice_event` rebuild);
  - `suggestion_skip`;
  - the widened `saved_view.sort_order` CHECK (F1).

  **Reason:** each one touches the same append-only and merge rules (data-model 7–14) and the same
  S1/S13 obligations. Two of them need a table rebuild. Designing them once costs less than
  designing them four times, and a single v2 → v3 upgrade is the only one the user's phone has to
  survive.

- **D21. Work that needs no schema change ships ahead of schema 3, as an early lane.** This
  replaces session 10's strictly sequential proposal (Suggest → schema 3 → triage → timer →
  scorecards → beauty). The early lane is:
  - Suggest v1 (shuffle plus coldness and hotness; skips always discarded);
  - Scorecards v1 (counts);
  - the ramp primitive.

  **Reason:** the user asked for a frontier that stays active without their re-injection. A lane
  that has nothing to wait on is the cheapest way to keep one. It also puts the radar on the phone
  early, and the radar is the control whose feel most needs the user's hands.

- **D22. Gates are hard or soft.**
  - **A soft gate is asked once, with a stated default.** If it is unanswered when its spec is
    written, the spec adopts the default and records it as an assumption. An overturned default
    becomes a follow-up package, and it never halts a lane.
  - **A hard gate blocks only its own package.**

  Hard gates: **G1** (it fixes a CHECK constraint, so a late change costs a table rebuild) and
  **G10** (beauty is the user's to direct). This is CLAUDE.md's "state the assumption explicitly
  in the journal", applied as a standing procedure.

- **D23. The session screen is a serialised hot file** (roadmap §2 rule 4). Suggest v1, triage
  plus Suggest v2, and the timer each own it in turn. **Triage and Suggest v2 are bundled as P9**
  because both read ratings on that screen.

- **D24. Suggester tuning is a per-device preference by default (G6),** following views.md V19's
  reasoning for the home View. This keeps it out of schema 3. Per-View tuning is deferred, not
  rejected.

- **D25. G1 is answered, so the four triage sorts are fixed (user, 2026-09-23: "Yes, fine").**

## Findings

- **F1. Adding the triage sorts is a schema change.** Adding them means widening
  `saved_view.sort_order`'s `CHECK (sort_order IN ('COLDEST_FIRST', 'HOTTEST_FIRST'))`
  ([saved_view.sq](../../shared/src/commonMain/sqldelight/dev/repertosaurus/db/saved_view.sq)
  line 57). SQLite cannot alter a CHECK, so it is a table rebuild. views.md V17a already warns
  that a new `SessionOrder` constant has to change three things: the constant, the CHECK and the
  parse. **So the triage sort names must be fixed before schema 3 freezes.** That is why G1 is a
  hard gate on P1.

- **F2. The Python migration emits no `feel`,** so widening feel to 0–3 does not engage CLAUDE.md's
  two-implementations rule. The workbook's `feel` column is the **groove** (`extract.py:1502`
  writes `facts["groove"]`). The only mention of `practice_event.feel` in `tools/import/` is a
  verification check (`build.py:993`, `feel NOT BETWEEN 1 AND 3`). That check stays correct for
  emitted data, which is always null.

- **F3. Session 10 §4 says its own notes are uncommitted. They are committed** in `c716923`, and
  `1a28fdb` follows it, but neither commit is pushed. Session 10's entry is left as written (the
  journal is append-only). This entry's §2 is the correct state.
