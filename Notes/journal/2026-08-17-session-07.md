# Session 07 — Editability, and the Fourth Id Fork

The database became editable from the phone. Three things that could only be seen by opening the
`.db` on a desktop — who the performers are, what they play, and who knows which song on which
instrument — are now first-class screens. The arc also turned up the fourth instance this week of
the project's signature failure, and this time it had already corrupted real data.

## Where we are

- **The capability editor ships.** Long-press a song → the feel sheet → *Who plays this*. One row
  per `(song, performer, instrument)`, grouped by performer, so Coralie is **one entry with two
  chips** rather than two entries.
- **The performer roster ships**, with the instruments each person plays **derived** from their
  capability rows, and a count of what points at them.
- **Every lookup table is reachable from the drawer** — instruments, tags, grooves, venues, bands,
  practice contexts, performers — with notes where the table has them.
- **253 shared tests + 35 instrumented tests, 0 failures.** No crashes at any point on the
  emulator, across two full UI passes.
- **Nothing is committed.** Three arcs now sit uncommitted in the working tree.
- **Nothing has run on physical hardware.** Still true, and now the largest remaining unknown.

## Decisions this session

Contract: [editing.md](../decisions/editing.md), E1–E47. The load-bearing ones:

- **E1 — recording a capability is not logging practice**, and the UI must never blur it. The two
  surfaces are now one long-press apart, which is why this is decision one and why it is proved by
  observation rather than inspection.
- **E3 / E10 — one row per `(song, performer, instrument)`, grouped by performer.** The user's own
  example is the spec: Coralie lead vocal *and* backing vocal, Charlotte on three parts.
- **E15 — the instruments a performer plays are derived, not stored.** No `performer_instrument`
  table. Accepted gap: a performer added before any song shows nothing, and the roster says
  "nothing points at it" rather than hiding them.
- **E23 / E24 — the practice logger is the root and back reaches it in at most two presses.**
- **E12 / V11a — View eligibility excludes soft-deleted performers and instruments.** Latent until
  this arc made deletion reachable; amended deliberately rather than discovered in the field.

2. **E22's first draft cleared optimistic taps on a View switch** — reversed last session and worth
   restating, because the same instinct nearly repeated here.
3. **The repository's split deferral expired and I had to notice.** The architecture review granted

   pass. E30–E32 record the expiry, take the cheap first cut now, and make the rest its own work.
4. **E35 — `capabilities()` and `lineUp()` returned the same rows in different instrument
   orders.** Two surfaces, one dataset, two answers. The test compared a *set*, which is exactly
   how it survived review the first time.

## The fourth id fork, and why this one is different

`normalise` diverged between Kotlin and Python **twice over**:

- **Astral letters.** Kotlin iterates UTF-16 units, so both halves of a surrogate pair fail
  `isLetterOrDigit` and a non-BMP letter is deleted; Python's `\w` keeps it.
- **Numeric categories No and Nl.** Python's `\w` matches `½`, `Ⅰ`, `①`; Java's `isLetterOrDigit`
  rejects them. **This one had already bitten real data** — a title like *5½ Hours* kept its
  fraction in the migration and lost it in the core, yielding a different canonical key and a
  different UUIDv5 that would never converge.

Decision 4e already settles which side is right — letters and decimal digits only — so **Python
was the side corrected**, and the correction was proved to move nothing by rebuilding the database
and confirming every id in all 17 tables byte-identical.

**What makes this instance different is the fix.** The previous three were closed by changing both
sides and remembering to keep doing so. This one is closed by a **shared 39-vector normalisation
file that both implementations read**, verified by a Kotlin test and by `build.py` before it
derives a single row. Agreement is now mechanised rather than promised.

## What the reviewers caught that the tests did not

Three reviewers ran against this arc. The pattern worth keeping is that **two separate tests
agreed with the defects they were meant to catch**:

- The eight-combination filter test claimed "each line is a different set of songs"; three pairs
  were identical, because the fixture had no non-lead vocal row. The docstring asserted what the
  fixture could not demonstrate.
- The capability error test asserted `message != null` — and success and failure shared one field,
  so the assertion passed either way. **A test written from the same mental model as the code
  cannot catch the model being wrong.**

The compounding UI finding is the one to remember. Individually the four defects looked minor;
together they meant *an edit could silently revert while the screen said it worked*: the dialog
edited a snapshot captured at tap time, nothing was disabled during the write, two writes could
land out of order, and the error channel was painted in the success colour.

And the empty state was **actively false** — a View filtered on a just-deleted performer rendered
*"No songs yet. Use Import to load your database file"* on a phone holding 479 songs, pointing at
the one destructive path in the app. It now says the filter names something removed, states
plainly that **"your songs are all still here"**, and offers the View editor.

## Process lessons

1. **Run it, and prove the negative by observation.** E1 was verified by counting `practice_event`
   before and after a full editing session — 826 → 826 while `song_performer` went 595 → 596 —
   rather than by reading the callbacks. Twice, on two different binaries.
2. **A guard that prints is not a guard.** `build.py :: verify()` measured the motivating View's
   231/138 and then did not check it. It now asserts and fails the build; fed 230/137 it exits
   non-zero.
3. **When two implementations must agree, ship the vectors, not the intention.** See above.
4. **Assert order as a list, never as a set**, when order is the thing under test.
5. **Scope the reviewers out of each other's lanes and out of the module being concurrently
   edited.** Running the Compose review read-only alongside a core fix pass cost nothing and
   collided with nothing.

## Open

- **Song field editing** — title, artist, key, tempo, decade, groove, tags. The largest remaining
  hole in "everything is editable", deliberately deferred so it would not delay the capability
  editor. **This is the next arc**, and the user has been asked whether to bring it forward.
- **E32 — the repository split by aggregate.** `CapabilityStore`, `SongCatalog`, `SavedViewStore`,
  `PracticeLog`. Must land **before** phase 2's sync adapter adds ~40 more methods.
- **Set list creation and editing** — the tables exist and nothing in the app touches them.
- **`JUNCTION_KEYS` is still two hand-maintained copies** in `extract.py` and `Uuid.kt` with
  nothing enforcing agreement — the same shape as the fork closed this session, in the one place
  the project has already been burned. The normalisation vector file is the template for fixing it.
- **A `Will/Coralie` performer row** with zero capability rows, a duet marker that leaked into the
  performer table. Now visible in the roster and pickable, yielding an empty result.
- **Attaching a practice context when logging** — the vocabulary is manageable; the logging path
  still cannot set one.
- **Nothing has run on a phone.** Touch ergonomics, real write latency, gesture-nav conflicts with
  the chip row, and dark mode are all untested by definition.

## In flight

Nothing dispatched. **Everything is uncommitted** — the Views, schema-compatibility and editing
arcs, plus their specs and this journal.
